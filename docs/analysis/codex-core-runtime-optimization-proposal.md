# Codex core 运行时对 goagent 的优化建议

日期：2026-10-21
状态：草稿提议
性质：基于两边源码阅读的优化建议，尚未实施；不改变现有代码、公开 API 或存储格式。

参考来源：openai/codex main 分支源码快照（2026-10-21 下载）。文中 Codex 行号以该快照为准，路径相对 `codex-rs/`；goagent 链接指向当前仓库。

## 结论

goagent 运行时在"进程崩溃后还能接着跑"这件事上，已经比 Codex 的 core 更完整：工具执行记录、结果未知的处理、检查点与消息确认的原子提交、跨进程的线程占用声明和递增占用编号，Codex 没有同等强度的机制。Codex 值得借鉴的是另一面：

- 每一步先把"这一步允许模型看到什么、允许执行什么"冻结成一份快照；
- 外层还有一层任务循环，专门接住模型已经给出终稿之后才到的输入；
- 工具是否并行按单个调用判断，不能因为其中一个工具要求串行，就让整批退化；
- 上下文超限时，先就地压缩再重试一次，不让整个运行直接失败。

下面按"先修正确性、再修吞吐、最后修规模"的顺序展开。

---

## 一、先划边界：这些已经领先，不要动

以下几项是 goagent 的强项，换成 Codex 的进程内做法反而会退步：

- 工具调用先登记再执行，结果未知有专门处理：[agent/exectools.go:341](../../agent/exectools.go#L341)、[checkpoint/durable_memory.go:272](../../checkpoint/durable_memory.go#L272)。
- 检查点、消息确认、占用声明、工具执行状态一次性提交：[agent/durable_runtime.go:321](../../agent/durable_runtime.go#L321)。
- 线程级占用冲突和恢复要求是明确错误，而不是让调用方自己猜"是不是忙"：[checkpoint/coordinator_file.go:19](../../checkpoint/coordinator_file.go#L19)。
- 人工审批暂停与恢复、跨进程队列和运行记录、工作流与子代理隔离，这些 Codex 没有同等完整的实现。

所以下面的建议都是"补一层"，不是"换一套"。

---

## 二、逐项对照

| 能力 | Codex core 的做法 | goagent 现在 | 判断 |
|---|---|---|---|
| 每步执行视图 | 每次采样前固化 `StepContext`（设置、MCP 连接、环境、token 预算）；设置更新下一次采样才生效 | 请求、工具解析、串行判断分三次读可变状态 | 有真实缺口 |
| 终稿之后的输入 | 外层任务循环，检查还有没有待处理输入，有就再跑一轮 | 直接返回；运行中追加的消息会被丢掉 | 有真实缺口 |
| 工具并发 | 按单个调用判断；并行用读锁，串行用写锁，串行调用只挡住重叠部分 | 任意一个工具要求串行，整批退化为串行 | 吞吐缺口 |
| 上下文超限 | 把压缩当成运行时动作，可以再次触发 | 只在每步开头压缩；上下文长度错误被当作不可重试的 400 | 有真实缺口 |
| 输入通道 | 统一输入队列，可中断当前模型请求 | 临时消息和持久收件箱两条通道，无回执、无抢占 | 部分缺口 |
| 工具批次崩溃一致性 | 执行前记录在途批次 | 先登记工具，批次结束才写检查点 | 部分缺口，有执行记录兜底 |
| 实时状态 | 活动轮次加事件流 | 只读头部检查点，明确说明不能判断"现在有没有在跑" | 观测缺口 |
| 工具暴露 | 六种暴露级别，支持按需发现 | 所有工具每步全量广播 | 工具规模变大后的缺口 |
| 审批与沙箱 | 统一执行器：审批、沙箱选择、拒绝后升级重试 | 审批在中间件，沙箱写死在 exec 工具里 | 一致性缺口 |
| 会话忙时 | 启动新轮次或追加到当前轮次 | 每次都新建运行，冲突时直接报错 | API 缺口 |
| 跨进程控制 | 不是设计重点 | 队列、运行记录、占用声明都完整 | goagent 领先 |

## 三、P0：四个马上值得做的改动

### P0-1 引入 `StepView`：每步冻结一份执行视图

**现在的问题。** 一个步骤里，模型看到的工具、审批看到的工具、真正执行的工具，是三次独立读取：

- 组装请求时广播工具：[agent/loop.go:224](../../agent/loop.go#L224)；
- 中间件随后还能改请求里的工具列表：[agent/loop.go:227](../../agent/loop.go#L227)；
- 执行时才按名字重新解析工具：[agent/exectools.go:310](../../agent/exectools.go#L310)；
- 是否串行也在执行时才判断：[agent/exectools.go:147](../../agent/exectools.go#L147)。

由此产生三种不一致：中间件加进请求的工具，执行时找不到；广播之后被移除的动态工具，模型能调用但执行不了；同一个工具的串行标记在广播和执行时可能不同。恢复运行时，也可能广播出一套和当初不同的工具。

**Codex 的做法。** 每次采样前固化 `StepContext`，把设置、MCP 连接、环境、token 预算等一次性捕获：`core/src/session/step_context.rs:23`。设置的更新走 `ArcSwap`，下一次采样才生效：`core/src/session/turn_context.rs:344`。也就是说，"这一步用哪套配置"不会中途变化。

**建议的形态。** 在合并完本步输入、调用 `BeforeModel` 之前，构造一个只读的 `StepView`，至少包含：

```go
type StepView struct {
    Settings   StepSettings        // 模型、温度、工具选择策略
    Tools      ToolView            // schema 列表 + name→工具实例 + 串行标记 + 暴露级别
    Context    ContextPlan         // 本步压缩/裁剪的结果与预算
    History    []core.Message      // 本步实际发送的历史
}
```

之后请求组装、工具审批、执行、检查点全部只读这个视图。`AddTool` 写"下一步视图"的待生效区，不再直接改当前请求；如果某中间件确实要影响当前调用，就显式标记视图失效并在发送前重建。检查点里记录本步广播的工具名和设置版本，恢复时按同一份视图重建。

**代价。** 一个结构体，加上把视图传到五六个调用点；`AddTool` 的语义要改文档。收益是给后面三个 P0 提供可测试的边界，也让"广播的工具一定能执行、执行的工具一定广播过"变成可以断言的不变量。

### P0-2 拆出外层任务循环：接住终稿之后才到的输入

**现在的问题。** 运行中追加的消息只在每步开头读取：[agent/loop.go:181](../../agent/loop.go#L181)。模型给出最终回答后，代码在 [agent/loop.go:264](../../agent/loop.go#L264) 直接提交并返回。如果消息在最后一次模型调用期间到达，它留在队列里，运行结束后随运行上下文一起丢弃。`Run.Steer` 没有返回值，也不检查运行是否已经结束：[agent/run.go:144](../../agent/run.go#L144)、[agent/runtime.go:116](../../agent/runtime.go#L116)，调用方完全不知道消息没被处理。

**Codex 的做法。** 外层是任务循环，内层跑完一轮后检查还有没有待处理输入，有就带着空输入再进一轮：`core/src/tasks/regular.rs:104`。判断依据是输入队列的待处理状态：`core/src/session/input_queue.rs:446`。

**建议的形态。** 把现在的 `run` 拆成 `runTask`（外层）和 `runSteps`（内层）。内层返回终稿后，外层做四件事：

1. 先关闭输入队列，再读取剩余消息，保证"检查之后才到的消息"不会静默进入一个已经结束的运行；
2. 有剩余消息就追加到历史，发布本轮的 `TurnDone`，再发布下一轮的 `TurnStarted`，继续跑；
3. 没有剩余消息才提交终稿并结束；
4. `Steer` 返回一个回执：已消费、待处理、已拒绝。运行关闭后调用返回"已拒绝"，不再无回执。

有两个实现细节必须一起改：

- 终稿的检查点现在以"释放占用"提交：[agent/loop.go:269](../../agent/loop.go#L269)。如果还要继续跑，必须改成不释放；否则别的运行可以在本运行继续写历史时拿到同一线程的占用。最终释放交给运行驱动那层：[agent/run.go:259](../../agent/run.go#L259)。
- `maxTurns` 现在是整个运行的预算。追加消息会消耗步数，这一点要写进文档，否则用户会疑惑为什么"只问了一句"却用完了轮数。

**代价。** 循环结构小改，`Steer` 的签名要变，补"终稿瞬间到达消息"的竞态测试。

### P0-3 工具并发按调用粒度判断，不再整批串行

**现在的问题。** 一个批次里只要有一个工具声明 `SequentialTool`，整批都退化为串行：[agent/exectools.go:147](../../agent/exectools.go#L147)。也就是说，模型一次发了十个只读查询加一个必须串行的写操作，十个查询也要排队。

**Codex 的做法。** 路由层按单个调用判断能不能并行：`core/src/tools/router.rs:246`。执行层并行调用拿读锁、串行调用拿写锁：`core/src/tools/parallel.rs:214`。串行调用只挡住与它重叠的部分，不会让整批排队。

**建议的形态。** 把调用序列按串行工具切成若干段。每段内部并发执行，段与段之间等待；串行工具单独成段、独占执行。结果仍按模型给出的顺序组装。全局的"本代理强制串行"保留，作为应急开关。状态写入已经有 `checkWriteAccess` 保护，这次改动只动调度，不动状态一致性。

**代价。** 中等。需要可控的假工具来断言"串行工具执行时没有别的工具在跑"和"结果顺序不变"。

### P0-4 上下文超限：压缩一次，重试一次

**现在的问题。** 压缩只在每步开头发生：[agent/loop.go:202](../../agent/loop.go#L202)。错误分类只有 `StatusError` 和"是否可重试"：[llm/error.go:14](../../llm/error.go#L14)。上下文长度超限通常是 400，而 400 被明确判为不可重试：[llm/error.go:28](../../llm/error.go#L28)。一次估算偏差或一条超大工具结果，就能让整个运行失败。

**Codex 的做法。** 它把上下文窗口当成运行时状态管理，压缩可以作为一次独立任务再次触发，而不是只在每步开头做一次固定动作。

**建议的形态。** 增加一个明确的错误类型，例如 `llm.ContextLengthError`，带上提供方、上限和本次请求的估算量。模型调用返回这个错误时，如果本步还没有执行过任何工具、没有副作用，就调用同一条压缩路径（降低目标、保留最近消息），基于 `StepView` 重建请求，重试一次。压缩结果写进检查点并发一个事件。第二次仍失败就把类型化错误返回给调用方。重试次数可配置，默认一次。

**代价。** 压缩本身要花一次模型调用和 token，必须防止递归。测试用假提供方模拟"第一次拒绝、压缩后接受"和"压缩后仍拒绝"。

## 四、P1：把输入和崩溃边界补完整

### P1-5 合并输入通道，增加投递阶段和抢占

现在运行中的临时消息和持久收件箱是两条通道，在同一大步里分两次读取：[agent/loop.go:181](../../agent/loop.go#L181)、[agent/loop.go:184](../../agent/loop.go#L184)。它们没有统一的投递阶段，也没有"消息到了要不要打断当前模型请求"的选项。

Codex 的输入队列会监听用户输入：`core/src/session/input_queue.rs:295`，每个采样步骤还带一个抢占标记：`core/src/session/step_context.rs:26`。

建议合并成一个输入队列，每条消息带三样东西：来源（临时消息、持久收件箱、工具结果、系统提示）、投递阶段（下次模型调用前、本次模型调用后、工具批次后、下一轮）、回执（已消费、排队中、已拒绝）。持久收件箱作为这个队列的持久层，临时消息不落盘。抢占先做成可选：只对"用户明确要求停止当前生成"的消息取消当前流，普通追加消息仍然等下一步。

### P1-6 工具批次执行前写一次在途检查点

现在工具调用在执行前先登记：[agent/exectools.go:341](../../agent/exectools.go#L341)，但包含工具调用的助手消息要到整批结束后才写检查点：[agent/loop.go:331](../../agent/loop.go#L331)。在途执行记录只在人工审批暂停时才写：[agent/loop.go:400](../../agent/loop.go#L400)。如果进程在批次中途退出，头部检查点里没有这条助手消息，执行记录里却可能留下已登记或结果未知的调用。

更麻烦的是调用编号的算法把调用 ID、工具名和参数一起算进哈希：[agent/exectools.go:416](../../agent/exectools.go#L416)。恢复后模型重新发起调用，只要调用 ID 或参数有变化，就会生成一个新的调用编号，旧的那条成为孤儿，而它的副作用可能已经发生。

建议在执行前提交一次检查点，内容是"助手消息 + 计划执行的调用 + 在途执行记录"，并标记一个区别于"审批暂停"的阶段。恢复时走和工具恢复相同的路径：先按登记状态判断已完成、未知还是可重试；再扫描执行记录，把检查点没有覆盖的登记标记为未知并告诉模型。`RunStatus` 不能把在途状态当成暂停，否则界面会误报"等待人工审批"。代价是每步多一次提交；可以先只对非幂等工具开启。

### P1-7 增加实时状态投影

`RunStatus` 只读头部检查点，文档已经明确说它不能回答"现在有没有在跑"：[agent/run_status.go:44](../../agent/run_status.go#L44)。跨进程的运行监听目前是轮询：[runstore/watch.go:55](../../runstore/watch.go#L55)，等待运行完成也是轮询：[queue/run_client.go:82](../../queue/run_client.go#L82)。

建议分两层：

- 进程内增加一个运行登记表，记录线程当前的活动运行、阶段（准备、调用模型、执行工具、等待审批）、步数和开始时间。它只是投影，进程崩溃就丢，永远不参与正确性判断。
- 跨进程利用已有的占用声明和续租信息，让 `RunStatus` 额外报告"谁持有占用、最近一次续租是什么时候"。这仍然是一次纯读，不改变现有语义。

### P1-8 会话忙时给出明确策略

`Session.Send` 每次都新建运行：[agent/session.go:47](../../agent/session.go#L47)。同一线程上已有运行时，调用方拿到的是占用冲突或"需要先恢复"的错误：[checkpoint/coordinator_file.go:19](../../checkpoint/coordinator_file.go#L19)。这其实是"忙"，不是失败。

建议增加 `WithIfBusy` 选项：直接失败、追加到当前运行、持久排队。返回值里带一个提交结果：已启动、已追加、已排队。追加需要 P1-7 的登记表找到当前运行；排队可以直接用现有持久收件箱：[agent/inbox.go:15](../../agent/inbox.go#L15)。这一步会倒逼 P0-2 把"运行关闭"的边界定清楚。

## 五、P2：工具规模上来之后再做

### P2-9 工具暴露级别与按需加载

现在所有静态工具每步全量广播：[agent/loop.go:96](../../agent/loop.go#L96)。技能工具已经证明"按需加载"可行：[skills/tool.go:18](../../skills/tool.go#L18)，但它只服务于技能，不是通用机制。

Codex 有六种暴露级别：`tools/src/tool_executor.rs:51`。不必全抄，先做三种：直接广播、可发现但不广播、完全不暴露。再加一个 `load_tool` 元工具，模型先搜索再加载。加载只影响下一步的 `StepView`。工具数量超过二三十个、或者接入大量 MCP 工具时，这个改动的收益才明显；太早做会让弱模型找不到工具。

### P2-10 统一执行策略

现在审批在中间件，沙箱固定在命令工具内部：[tool/exec/exec.go:27](../../tool/exec/exec.go#L27)。以后文件工具、MCP 工具也需要同样的规则时，就会出现三套各写各的判断。

Codex 用一个统一执行器处理"要不要审批、用哪个沙箱、第一次被拒绝后要不要升级重试"：`core/src/tools/orchestrator.rs:125`。建议给每个工具声明一份执行策略：审批级别、沙箱配置、拒绝后是否重试。所有工具族走同一条执行路径，人工审批中间件只负责展示和收集决定。等真正接入第二类需要沙箱的工具时再做。

## 六、目标架构

```text
Agent / Session
 ├─ LiveRunRegistry        进程内投影：谁在跑、跑到哪个阶段（可丢，不参与正确性）
 ├─ InputQueue            临时消息 / 持久收件箱 / 工具结果
 │                        每条带来源、投递阶段、回执；持久收件箱作持久层
 └─ Run
     ├─ RunContext        状态、存储、事件总线、占用声明与递增编号、运行预算
     ├─ TaskLoop          外层：内层给出终稿后，检查剩余输入；有就续跑
     └─ StepLoop          内层：一步一个 StepView
         └─ StepView      本步冻结
             ├─ SettingsSnapshot   模型、温度、工具选择
             ├─ ToolView           schema + 名字到实例 + 串行标记 + 暴露级别
             ├─ ContextPlan        压缩/裁剪结果与预算
             └─ Request            由上面三项推出，模型只看这一份
```

对应的两个循环：

- **外层任务循环**：准备 → 内层循环 → 终稿且输入队列为空 → 结束；终稿但还有输入 → 追加并继续；暂停 → 写检查点并返回。
- **内层步骤循环**：构造 `StepView` → 调模型 → 有工具调用就审批、分段执行、写检查点 → 下一步；没有工具调用就交回外层。
- **崩溃边界**：执行工具前写一次在途检查点；恢复时先用执行记录判断结果，再用 `StepView` 重建同一套工具，避免模型重新发起调用时绕过旧登记。

## 七、不该照抄的部分

- **不要用进程内的单轮互斥替代线程占用声明。** goagent 的占用、递增编号和跨进程运行记录更强，Codex 的互斥只覆盖单进程。
- **不要换成 Codex 的 rollout 文件持久化。** goagent 的"检查点 + 确认 + 工具状态"原子提交更适合断点恢复和跨进程。
- **不要一开始就做六种工具暴露级别。** 没有代码模式的情况下，三种足够。
- **不要急着抽任务类型层级。** Codex 把普通对话、审查、压缩、用户命令拆成任务，是因为它确实有这四类；goagent 现在只有一个循环，先拆出外层循环，等出现第二种真实任务再抽象。
- **中断工具的结果语义要明确选择。** Codex 记录"被中止"的结果，goagent 选择"结果未知"并交给恢复策略处理。后者更安全，不要为了对齐而改掉。
- **平台相关的沙箱机制按需引入。** goagent 现在的可移植策略（超时、输出上限、目录限制、环境白名单、命令白名单）已经够用，等产品确实要求操作系统级隔离再说。

## 八、落地顺序

| 顺序 | 改动 | 完成标志 |
|---|---|---|
| 1 | `StepView` | "执行的工具一定在本步广播过、广播的工具一定能解析"成为断言 |
| 2 | 外层任务循环 | 任何阶段追加的消息，要么被消费，要么拿到"已拒绝"回执，不再静默丢失 |
| 3 | 按调用粒度并发 | 串行工具是屏障，不是整批锁；结果顺序稳定 |
| 4 | 上下文超限重试 | 只压缩一次、只重试一次；第二次失败返回类型化错误 |
| 5 | 统一输入队列 + 在途检查点 | 每个阶段边界注入崩溃，恢复后不重复执行、不丢输入 |
| 6 | 实时状态 + 忙时策略 | 界面不再把"没提交"误判成"没在跑"；同一线程的第二个请求有明确去向 |
| 7 | 工具暴露 + 统一执行策略 | 工具规模变大后提示词不膨胀；审批和沙箱规则只有一处 |

如果只做一件事，先做 `StepView`：它不改公开行为，却能让后面三项的测试有可靠边界。如果只修一个问题，先修终稿后的消息丢失：这是唯一会让调用方以为"已处理"、实际没有处理的缺口。
